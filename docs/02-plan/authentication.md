# Authentication

Use Auth.js Credentials with email and password, encrypted JWT cookies and the existing User model. The application owns password, activation and revocation logic. A database-session adapter adds storage and does not fit the proposed Credentials flow. OAuth delegates password handling but requires provider accounts and verified allowlisting. Magic links require mail delivery and operational handling of deliverability. The approved manual invitation workflow suits the pilot. [Auth.js Credentials](https://authjs.dev/getting-started/authentication/credentials) · [Auth.js Next.js reference](https://authjs.dev/reference/nextjs)

| Operation | Behavior |
| --- | --- |
| Bootstrap Super Admin | An authorized operator runs an idempotent terminal provisioning command with an explicit normalized email. Create INVITED with no tenant. Generate an activation link through the same token service. A second run does not overwrite an existing identity. Record bootstrap via a sanitized operator record and later platform activity where an authenticated actor exists. |
| Provision wholesaler | Super Admin creates business INACTIVE, provisions an INVITED account attached to that business, and activates the business when ready. Either step may be retried safely. Deliver the activation link through a verified private channel. Reissue replaces the old token. |
| Activate | Show password setup on /login#activate. Prefer a fragment-contained token cleared from browser history after extraction. Send the token only in a same-origin JSON POST. A random 256-bit token is stored only as a digest, expires after 24 hours and is atomically consumed when password is set. Activation sets the user ACTIVE. Business access still requires an ACTIVE business. |
| Login | Zod parses email and password. Check a persistent rate limit by trusted requester and normalized identity digest before verifying with a uniform invalid-credentials response. Use a dummy hash for missing accounts and redact login values from telemetry. Redirect active users to /admin/dashboard or /dashboard using a same-origin allowlist. |
| Session | JWT stores subject and session version. Secure, HttpOnly, SameSite=Lax cookies in production. Use an eight-hour maximum from sign-in, checked from an immutable issued-at claim even if the library refreshes its token. Reload User and Business for protected actions. Never accept role or tenant changes from session update payloads. |
| Logout | Auth.js same-origin, CSRF-protected sign-out clears the cookie. Password change or operator reset increments session version, revoking all prior sessions. Password change requires the current password. |
| Suspend account | Atomically update status and increment session version. Existing cookies fail the next protected check. Reactivation requires a fresh sign-in. Invited users are restored through reissued activation. |
| Suspend business | Mark business SUSPENDED and increment visibility version. Existing tenant sessions lose access on the next request and public resources disappear. Still-valid account cookies may resume after business reactivation. Suspended businesses cannot initiate new tenant sign-ins. |

Use a salted memory-hard KDF such as Node's scrypt with reviewed parameters, constant-time verification and bounded concurrency. Require at least 12 characters, permit passwords up to 128 characters with no silent truncation, and rate-limit activation, sign-in and password changes. Operator-assisted resets reuse single-use activation and revoke all sessions when issued. Auth.js owns its auth callback CSRF protection. Require a canonical same-origin check for custom cookie-authenticated writes. A protected API returns 401 for missing or revoked sessions and 403 for role or business policy denial. See [route protection](application-routes.md) and [permissions](authorization-matrix.md).
